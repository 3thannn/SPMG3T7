# Test cases for SPMG3T7 (read by docs/testing/build_workbook.py, not a YAML file), derived from the acceptance criteria in acceptance_criteria.yaml
# with the Week 4 method: one happy path per AC, one negative per distinct rule in it, a
# boundary case only where the AC has a limit, and cross-cutting checks once (in US1.3)
# rather than in every story. Each test case names the one automated test that runs it.
#
# Fields follow the Week 4 test case template:
#   id, ac, category (Happy path | Negative | Boundary | Cross-cutting | Technical), scenario,
#   preconditions, steps, data (test data), expected (expected result),
# plus: layer (API integration | Unit | Component | E2E | DB integration), test (the
# automated test: backend `path::Class::test`, frontend `path::title`), and why (what would
# go wrong without it).
# Technical store cases name one representative test; their why field explains
# the related adapter checks grouped under that case. These do not add new Jira ACs.

- id: TC-US1.1-01
  ac: US1.1-AC1
  category: Happy path
  scenario: Each role signs in with valid credentials and is sent to its own view
  preconditions: One seeded account per role
  steps: POST /auth/login with the role's email and password
  data: The seven seeded accounts, e.g. organiser@spmg3t7.edu with the shared test password
  expected: 200; the session names the role and carries a token; home is the role's view
    (Organiser and Coordinator /events, Lead /unassigned-queue, Venue Staff /venues, Safety
    Officer /safety-review, Technical Support /equipment-requests, Attendee /attend)
  layer: API integration
  test: backend/tests/test_auth_login.py::test_each_role_is_told_where_its_own_view_is
  why: The role-appropriate view is decided by the server. One case per role, because each
    role is its own equivalence class.
